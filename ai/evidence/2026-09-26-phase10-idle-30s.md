## Unplanned result: replay is deterministic across machines

This capture was replayed on the **Pi 5 (aarch64, Debian Trixie)** and
independently on the **Mac (arm64, macOS, Python 3.14)**, producing byte-identical
reports — same frame counts, same packet counts, same session, same state.
Nothing was designed for this, but it is worth recording: **the replay path has
no host-dependent behaviour**, so a report from either machine is citable.

## What the longer window adds

The 5 s capture was clean but small. Thirty seconds is where marginal signal
integrity would begin surfacing as occasional resyncs.

- **Zero CRC failures across 765 frames and 1.09 MB.** At 79.2 % wire occupancy
  this is the most that can be said for idle RX without a longer soak.
- **A single stable session id** — no mid-capture reboot.
- **`buffered_at_end 0`** — the stream ended on a frame boundary with no partial
  frame stranded, so the scanner consumed everything it was given.

# Failure behaviour — runbook steps 8 and 9, offline

Both exercised against **derived in-memory copies** of the fixture above. The
artifact is never modified: `test_fixture_is_unmodified` asserts its SHA-256 on
every run, and it was verified unchanged after the full suite. No mutated
capture is committed — the tests derive each mutation at runtime, so the
regression coverage is permanent without a second artifact.

**765 frames were located independently** by walking the stream and verifying
each CRC, matching the replay's count exactly. The first frame begins at byte
1 664, which is the discarded count.

## Step 8 — CRC rejection

The mutation was chosen to **matter**, not to be arbitrary:

| | |
|---|---|
| Target | First HELLO, `payload[18]` = `session_id` low byte |
| Absolute byte | **25 400** (frame at 25 377, verified type `0x06`) |
| Original → new | `0x04` → `0x63` (**session 4 → 99**) |

Had CRC not caught this, the receiver would conclude the Teensy had rebooted,
**discard the entire session and restart at `UNKNOWN`**. So this proves CRC
protecting a field whose corruption has consequences, rather than proving the
scanner can resynchronise after garbage.

**Observed:** ≥1 CRC failure · `frames_ok` 765 → **764** · `Hello` 30 → **29** ·
`hello_session_ids` **still `[4]`** — 99 never reached the model ·
`measurement_state` `IDLE` · `return_source` `TS`.

### 🔍 The measured cost of one lost HELLO

The corrupted HELLO is the **first** one, so geometry is unavailable until the
next announcement. The effect is precise:

| | Clean | HELLO #1 corrupted | Δ |
|---|---:|---:|---:|
| promoted `LiveFrame` | 631 | 610 | **−21** |
| `geometry_unavailable` | 14 | 35 | **+21** |
| **total live frames** | **645** | **645** | **0** |

**21 frames at 21.5/s = 0.98 s, against a 1.0 s re-announce period.** Nothing is
*lost* from the stream — promotion is **deferred by exactly one HELLO interval**
and then self-heals.

**This is TODO-56's value proposition measured rather than argued.** Before that
fix HELLO was sent once at boot, and losing it meant the Pi could **never**
decode a RESULT until the Teensy rebooted. It now costs one second.

`STATE` and `ROUTER_STATUS` counts are **unchanged** (60 and 30), because
neither needs geometry — which is exactly why STATE can repair a measurement
state while live frames are still undecodable.

**Second corruption site**, in the largest packet type after geometry exists: a
payload byte in a 1 689-byte LIVE_FRAME. A 1 689-byte frame is 36× a HELLO and
resync rescans the whole rejected payload, so this is where a resync bug would
swallow a neighbour. **Exactly one live frame lost; HELLO, STATE and ROUTER
counts all unchanged.**

## Step 9 — unknown packet type

Injected a **well-formed** packet — valid sync, valid length, **valid CRC** — of
type `0xFE` with a 32-byte payload, at byte **61 007**, a verified frame
boundary (the following two bytes are `55 aa`). This tests **forward
compatibility**, not error handling.

**Observed:** `unknown_types {0xfe: 1}` · `frames_ok` 765 → **766** ·
**`crc_failures` 0** — a valid-CRC unknown type is not read as corruption ·
`LiveFrame`, `StatePacket`, `RouterStatus`, `Hello` counts **all identical to
clean** · `hello_session_ids [4]`, `measurement_state IDLE`, geometry and the
**entire router status byte-identical** to the clean replay.

A degenerate case was also checked: type `0xFD` with a **zero-length** payload.
Handled, no CRC failures, state intact.

### Tolerated and unremarkable are different things

The **parser** skips the unknown type by length and continues. The **report**
still flags it, and `transport_ok` becomes false — because in a capture from our
own firmware an unknown type means producer and consumer disagree about the
protocol. **Both layers are correct**, and the tests assert both: the packet is
survivable *and* it is not silently normal.

## A test that was wrong, and the failure was the finding

The first version of the CRC test asserted the `LiveFrame` count was
**unchanged**, on my assumption that a dropped HELLO costs nothing. It failed at
610 ≠ 631 — and the failure produced the 0.98 s measurement above, which is a
more useful result than the assertion would have been. The corrected test
asserts the conservation law (promoted + blocked is constant) and the interval,
rather than an absence of effect that was never true.

## What steps 8 and 9 do NOT cover

These were exercised **offline against a recorded stream**, which is the right
place for them — deliberate corruption on a live link is neither controllable
nor repeatable. But note the bound: they prove the **receiver** rejects and
tolerates. They do not exercise the Teensy, the UART, or the physical layer, and
no corrupted byte was ever transmitted.
