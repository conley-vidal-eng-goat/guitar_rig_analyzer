**Two separate claims per coordinate — read this before reconstructing.** Every
location in this document asserts two things, and they do not carry the same
confidence:

| Claim | Confidence | Why |
|---|---|---|
| **Which column, and which side of the centre channel** | `PHYS` | Load-bearing and electrically meaningful. Getting this wrong builds a different circuit |
| **Which row letter within that strip** | `RPT` | Builder-reported only. Electrically immaterial on an intact strip, but **this is exactly what a hole-for-hole rebuild claims to specify** |

Unless a row states otherwise, read every coordinate as `PHYS` at strip level and
`RPT` at hole level. A `RPT` row letter is a good-faith bench report, not an
observation anyone has independently confirmed. Do not cite one as established.

**Critical adjacency rule.** A column's A–E holes and its F–J holes are
**separate nodes**. The build depends on this: col 38 A–E is U1 pin 4 (GND)
while col 38 F–J is U1 pin 5 (OPA_BIAS). Same for cols 35, 36, 37.

### ⚠️ Data-line naming convention — read before citing I2S_DIN / I2S_DOUT

**Net names on this project are CODEC-REFERENCED (named from the SGTL5000's
point of view), not Teensy-referenced.** The two conventions are exact opposites
on the data lines, so the distinction has to be stated rather than assumed:

| Teensy pin | Codec-referenced (**used here**) | Teensy-referenced | Direction of data |
|---|---|---|---|
| **7** | `I2S_DIN` — the *codec's* data input | would be "DOUT" — the *Teensy's* data output | Teensy → codec |
| **8** | `I2S_DOUT` — the *codec's* data output | would be "DIN" — the *Teensy's* data input | codec → Teensy |

**Authority for the direction** (not the name): [config.h:81-85](../../firmware/guitar_rig_analyzer/config.h#L81-L85)
— *"pin 8 is I2S RX_DATA0 on Teensy 4.x … and carries Audio Shield line-in INTO
the Teensy"* — and [journal.md:1077](../../ai/journal.md#L1077) — *"Pin 8 is the
line carrying line-in audio into the Teensy."* Pin 7 is `SAI1_TX_DATA0`
(Teensy transmits); pin 8 is `SAI1_RX_DATA0` (Teensy receives).

**Authority for the name:** the codec-referenced convention is the one used
throughout this project — the original hardware brief, every journal entry from
2026-09-05 (13) onward that discusses "DOUT pin 8", and `config.h`. **Do not
flip these labels** without changing all three, or the entire DOUT debugging
narrative stops referring to the same wire.

The schematic carries this note on its face, plus direction arrows on every
signal line and the `SAI1_*` aliases inline, so neither reading can go wrong.

**Cross-check: the physical set matches the firmware exactly.** Pins 7, 8, 18,
19, 20, 21, 23 — the same seven derived independently from `AudioInputI2S`,
`AudioOutputI2S` and `AudioControlSGTL5000` in
[audio_capture.cpp](../../firmware/guitar_rig_analyzer/audio_capture.cpp). Physical observation and firmware
agree with no leftovers on either side.

**⚠️ Two orange wires in one bundle.** Pin 8 (`I2S_DOUT`) and pin 19 (`I2C_SCL`)
are both orange. **DOUT is the conductor that consumed days of debugging** across
journal entries (3), (4) and (5). A colour collision on that specific wire is a
real maintenance hazard: anyone re-seating the bundle from memory can transpose
them, and the failure would present as codec-control weirdness rather than as an
obvious data fault. Recorded, not changed — the bundle is frozen.

**Note on the 5V pass-through.** The SGTL5000 runs from 3.3 V. The green `5V`
wire replicates the pass-through that a stacked header would provide; whether any
Rev D circuitry uses it is `NYV`. It is part of the known-good state and stays.

### ⚠️ Teensy pins 0 and 1 are reserved — Pi 5 display link

**Added 2026-09-11 (ADR-001).** Pins 0/1 are `Serial1`, reserved for the binary
UART link to the Raspberry Pi 5, which
[ADR-001](../adr/ADR-001-display-architecture.md) establishes as the **production
display path**. Nothing is wired to them on this board — the reservation is a
forward declaration, `NYV` like the rest of the Phases 5–10 block — but it must be
honoured by any future pin assignment. `config.h` names them
`PI_LINK_UART_RX_PIN` / `PI_LINK_UART_TX_PIN` for exactly that reason.

**Why this note exists.** Until ADR-001 this reservation was real in the firmware
(TODO-24 rejected pins 0/1 as display-reset candidates on its authority) but absent
from this document and from the generated drawings, where the **RA8875 was the only
display entry in the reserved-hardware list**. The as-built record therefore
corroborated the architecture the project was drifting *away* from. Corrected in
both the netlist and `tools/gen_schematic.py`; the RA8875 row now reads
"SPI display (debug only)".

## 4a. Analog-section audit — 2026-09-07

Every net re-derived from the builder's raw bench statements, **not** from the
drawing or the runbook, in the order power → C1/input → U1A → U1B →
SOURCE/RETURN → shield. Three findings; two material.

### 🔴 A1 — Four capacitor values were never verified, and the one that *was* contradicts them

C3, C4, C5 and C7 were recorded as "0.1 µF". **The builder never read those
markings.** They were described only as *"yellow things"* — the same description
given for **C1, which turned out to be `BC103` = 10 nF, not 0.1 µF.**

So the single data point available directly contradicts the assumption applied to
the other four. `PHYS` covered their *presence and position*; it never covered
their *value*, and the table implied otherwise.

**Resolution:** the builder confirmed 0.1 µF at the bench on 2026-09-07, so the
values are restored — but tagged `RPT` (builder-reported), **not** `PHYS`, since
no marking was read back. The count slip
("all three" for four parts) was raised rather than absorbed, and is closed.

### 🔴 A2 — RETURN_NODE was missing from the schematic entirely

`RETURN_NODE_PHYSICAL_CH 1` ([config.h:174](../../firmware/guitar_rig_analyzer/config.h#L174)) binds
RETURN_NODE to I²S channel 1 = U3 **LINE IN R**, which **has no conductor
fitted**. The drawing simply omitted it, so a reader could not tell whether the
channel was absent by design, forgotten, or drawn elsewhere.

This matters more than an omission normally would: the firmware reports a level
for RETURN_NODE, and **−56 dBFS is the crosstalk floor from LINE IN L, not a
measurement** (journal 2026-09-07 (7)). An undocumented open input that still
prints a plausible number is the same class of trap as TODO-29's clamped TF bins.

**Resolution:** LINE IN R now drawn with an explicit IEEE no-connect cross and
annotated on the face of the drawing.

### 🟡 A3 — VGND's 2.50 V was stated as fact

It is **calculated** from R3/R4 being a matched pair. The only measurement,
2.480 V (journal 2026-09-05 (1)), predates the OPA_BIAS rework and was taken at
the old column-15 divider. Drawing now reads "2.50 V (calculated)".

### ✅ A4 — R5 = 100 kΩ is better supported than recorded, and is upgraded

Journal 2026-09-05 (6) measured a 1 kHz gain of **0.9848** through the input
network, against **0.9867** predicted for 100 kΩ with C1 = 10 nF. A materially
different resistor is excluded — 22 kΩ would predict ≈0.81. Independent of the
colour-band reading, and the same measurement independently corroborates
C1 = 10 nF. **`INF` → `DERIV`.**

### ✅ Verified with no defect found

Power entry and rail decoupling · GND bonding · VGND divider topology and its
grey `45c` jumper · OPA_BIAS divider, decoupling and 0.874 V agreement · C1 →
`33d`→`37d` → pin 3 · J1 tip/ring/sleeve including the taped ring · R5 into the
bias node · U1A follower via `35a`→`36a` · **C2 polarity** (+ on the 0.875 V
op-amp output, − on the ~0 V SOURCE_NODE — independently confirmed at
journal.md:1390) · U1 pins 4 and 8 with W1 and C3 · U1B termination via
`36i`→`37i` · SOURCE_NODE membership at column 48 · `48e` → LINE-IN-L.

## 4b. Digital-section value & provenance audit — 2026-09-07

Run after the topology and direction audits, in the order clocks → 5 V function
→ part identity, so that the best-evidenced claims established a baseline first.

### ✅ D1 — Clock frequencies: the strongest evidence chain in the document

Derived **and** independently measured, agreeing to within meter resolution:

| `I2S_MCLK` | 11.2896 MHz (256× Fs) | **~11.29 MHz** | `FW`+`MEAS` |

Scope figures from journal 2026-09-06 (1). **Defect found: `I2S_LRCLK` carried no
frequency on the drawing** while the other two did — an inconsistency that made
the frame clock look less established than it is. All three now carry value and
ratio, with the provenance stated on the sheet.

### 🟡 D2 — The 5 V pass-through's function was asserted, not established

The drawing read *"5V pass-through, unused by codec."* The **"unused"** half has
no primary source: the SGTL5000 runs from 3.3 V, and journal:1077 states *"the
shield runs from 3.3 V; it does not need 5 V"* — but that is a project assertion,
not a datasheet citation or a measurement, and it says nothing about whether
other Rev D circuitry uses the pad.

The wire is real and `PHYS`. **What the shield does with it is `NYV`**, and the
drawing now says so. Harmless either way, but a reconstructor should not be told
a pin is unused on this document's authority.

### 🟡 D3 — "SGTL5000" is a functional identification, not a package reading

The marking on U3's codec has never been read; the QFN is not legible in any
photo. The identification rests on two things: the Rev D silkscreen, and
`AudioControlSGTL5000::enable()` returning true
([audio_capture.cpp:349](../../firmware/guitar_rig_analyzer/audio_capture.cpp#L349)) — i.e. a device at the
SGTL5000 I²C address accepts SGTL5000 register writes. That is good evidence and
adequate for this document, but it is `DERIV`, not `PHOTO`.

**Board-revision assumption, now discharged.** Journal:962 raised *"whether the
shield is genuinely Rev D rather than a Rev C wired by pin number"* — a real risk,
since Rev C uses a different Teensy 3.x pin set. Closed three ways: silkscreen
read as "Rev D" (`PHOTO`), bench confirmation at journal:913, and the as-built
pin set 7/8/20/21/23 being the Rev D assignment, which now demonstrably works.

### Why this took three passes — worth keeping

Two candidates were raised and both were wrong, and the reasons differ:

1. **The "unaccounted-for blue jumper"** (photos 3/7/8/9/10) — *my error.* The
   builder's `38j`→`41c` jumper crosses the centre channel, which from these
   angles looks like a wire climbing toward the rail. **I asserted a conductor

2. **The bare staple near col 35** — *my error again.* It is at column 34 and is

**And the actual answer was visible in the photographs the whole time.** An
orange wire beside the adapter appears clearly in photos 10 and 15; I saw it,
and attributed it to the input side of the circuit rather than to pin 8.

**The methodological point, which is the useful part.** Three separate passes
over a 16-image set failed to identify a *power connection* that a single
directed look at the board found in seconds. Photographs were sufficient for
topology, component identity, geometry and the interconnect map — and
insufficient for exactly one class of question: **which of two adjacent rail rows
a conductor lands in.** That is the class where the physical board is not
substitutable, and it is worth knowing before the next capture.

**What kept this honest:** the gap stayed `NYV` through two failed candidates and
was never closed on plausibility. The runbook described this connection correctly
the entire time, and adopting its description on resemblance would have produced

## 6a. Engineering notes on the captured configuration

**Input high-pass corner ≈ 160 Hz.** C1 = 10 nF into R5 = 100 kΩ gives
1/(2π·100k·10n) = **159 Hz**. The low E string fundamental is 82 Hz, so as
captured this front end is **−6 dB at the bottom of the guitar's range**. This is
the runbook's acknowledged breadboard compromise, not a defect, but any
transfer-function measurement taken in this configuration carries that rolloff
and must not be attributed to the device under test. Swapping C1 to 100 nF would
move the corner to 16 Hz — **recorded as an option, not a recommendation, and not
to be done before the frozen state is signed off.**

**⛔ SUPERSEDED — J2 is gone.** *(Text retained; it described the frozen state.)*
**J2 is an open stub on SOURCE_NODE.** An unterminated jack hangs off the node
that feeds the codec. It contributes a small parasitic capacitance and acts as a
short antenna. Harmless at these impedances and levels, and it is part of the
known-good state, so it stays — but the schematic must show it, because a
reconstruction that omits it is not the circuit that was measured.

**What replaced it (2026-09-21, `PHYS/OBS`):** J2 is disconnected and **no
remaining conductor runs from SOURCE_NODE / col 48 to the former J2 connection.**
The stub is not a parasitic to model any more, and no Phase 9 procedure carries a
"J2 must stay empty" precondition. See §10.0.

```
                           K1 · RELAY_SEND · pin 14              K2 · RELAY_RETURN · pin 15
J4 ─ C1 ─ U1 ─ C2 ─ col48  ┌─ NC 56a ←─ 48e                 J6 Rig Return TS ─→ NC 15a ─┐
      = SOURCE_NODE ───────┤                                                              ├─→ COM 16a ─→ LINE IN R
                  │        ├─ COM 57a ──→ J5 Rig Send        J7 XLR pin 2 ──→ NO 17a ─────┘      = RETURN_NODE
                  │        └─ NO  58a ←── U3 LINE OUT L
                  └─ 48e ──→ U3 LINE IN L = SOURCE_NODE (ch 0)

  pin 14 LOW  = buffer output → Rig Send      (default, and the boot state)
  pin 14 HIGH = codec LINE OUT L → Rig Send   (monitor / injection path)
  pin 15 LOW  = TS return  → LINE IN R        (default, and the boot state)
  pin 15 HIGH = XLR return → LINE IN R
```

**Both defaults are the de-energised state**, so the board comes up in the
buffer-to-Rig-Send / TS-return configuration with no firmware action required.

## 14. Part II verification summary — and what is *not* evidence

**Bench-proven end to end, with a real signal** (journal 2026-09-19 (4), (5)):

| Chain | Result |
|---|---|
| Guitar → J4 → buffer → SOURCE_NODE → J5 → external TS cable → J6 → K2 NC → COM → LINE IN R | SOURCE **−10.1** / RETURN **−10.2 dBFS**, TF confidence **15 %** (threshold 10 %), 120 Hz / 500 Hz / 1 kHz all −0.0 dB, raw samples tracking |
| Stimulus-present TS/XLR A/B, both returns fed from one source | TS loop connected **−28.3 dBFS** · TS loop disconnected **≈ −68 dBFS** · XLR selected **−28.3 dBFS**, 1 kHz −0.0 dB |

**Confirms the routing convention: pin 15 LOW = TS, HIGH = XLR.**

**⚠️ What none of that establishes — the bounds belong with the numbers:**

1. **−0.0 dB is a cable loop, not a calibrated figure.** Unity through a short
   cable is the expected sanity outcome of a loopback, not a validated flat
   response. The calibrated path is the Phase 9 validation suite, **which has not
   been run.**
2. **15 % confidence is barely over threshold**, from a decaying non-stationary
   strum. It demonstrates validity, not quality.
3. **`---` at 5 kHz and 10 kHz means no qualifying data in those bins.** It is
   **not** evidence of roll-off.
4. **The XLR branch in the A/B was an adapter jumper from `SOURCE_NODE` to
   pin 2**, so "XLR signal present" was true by construction. What is proven is
   connector contact + relay transfer + codec input — not a rig loop.
5. **The noise-floor comparison TS vs XLR was never completed.** A TS-selected
   floor exists; an XLR-selected floor does not. One number is not a comparison,
   and R5 is the risk it would test.
6. **The grounding topology changed for that test** — the adapter tied XLR pin 1
   to Audio Shield GND while pin 3 stayed on the breadboard rail. Any future
   floor comparison must state which of the two topologies was in place.

## 15. Phase 9 validation topology — external, not fitted

Recorded here because it attaches to J5 and J6 and will be mistaken for board
hardware otherwise. **None of it is part of the permanent analyzer.**

```
external source → J4 Instrument In → C1 → U1 → C2 → col 48 = SOURCE_NODE
                                                   ├─► 48e → LINE-IN-L   = SOURCE (ch 0)
                                                   └─► 48e → 56a NC → 57a COM → J5 Rig Send
                                                             [ EXTERNAL FIXTURE UNDER TEST ]
                              LINE-IN-R ← 16a COM ← 15a NC ← J6 Rig Return TS = RETURN (ch 1)
```

**Preconditions: pin 14 LOW and pin 15 LOW** — both are the boot defaults.

**Why the generator drives J4 and never SOURCE_NODE.** Both the harness and the
runbook previously specified a Y-split onto SOURCE_NODE. Read literally that puts
an external generator in contention with the OPA1642 output. Driving the
high-impedance instrument input instead avoids it, and because **SOURCE is
measured at the fixture's input terminal and RETURN at its output**, the measured
transfer function is the fixture's own loaded voltage ratio — the driving
impedance, C2's reactance and the relay contact resistance all drop out. The
Y-split topology was replaced in `119a737`.

**Status:** approved in principle as the design basis. **Not authorized for
testing, and no hardware is to be built from the current Phase 9 instructions**
until the operator-facing text is reconciled (TODO-55). **The Test 4 RC fixture is
deferred pending a 100 nF film capacitor** — that is an external
characterisation-fixture dependency and **not a breadboard blocker. Do not fit a
substitute capacitor to satisfy it.**

**Construction complete ≠ signed off ≠ validated.** All three are tracked
separately, and Phase 9 remains incomplete.
